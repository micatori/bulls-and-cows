# DESIGN.md — Bulls and Cows

Документ описывает **игровое ядро** (`src/game/**`, `src/storage/**`) и то, как его
использует интерфейс (`src/ui/**`). Ядро не знает ни о DOM, ни о `localStorage`, ни о
`Date.now()`, поэтому тестируется в Node-окружении Vitest за доли секунды.

Запуск и проверка: `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`,
`npx http-server -c-1 .` (ES-модули не работают с `file://`).

---

## 1. Структуры данных

### 1.1 Секрет и попытка — `string`, а не число

`src/game/generateSecret.ts`, `src/game/state.ts` (`Attempt.guess`), `src/game/types.ts`.

| Требование задачи                            | Почему `number` не подходит                                                     | Почему `string`                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------- |
| «секрет может начинаться с 0», пример `0123` | `Number('0123')` теряет ведущий ноль, длина перестаёт равняться `config.length` | символы сохраняются как есть                       |
| системы bin/oct/dec/hex в одном поле         | для hex цифры `a`–`f` вообще не представимы числом                              | алфавит — просто набор символов (`DIGITS_BY_BASE`) |
| сравнение по позициям                        | нужна была бы арифметика выделений разрядов                                     | `s[i] === g[i]`, без арифметики вообще             |

Дополнительно: длина секрета — это `config.length`, а не «число разрядов», поэтому
представление длиной ровно `config.length` символов делает инвариант
`secret.length === config.length` видимым прямо в типе данных.

Массив символов (`split('')`) появляется **только внутри функций** — в
`evaluateGuess.ts` (`toDigits`) и `isValidGuess.ts` (`hasOnlyValidDigits`), — потому что
манипулировать элементами удобно только через `map/filter/reduce/every`. В состоянии и в
истории хранится компактный `string`: он сравнивается по ссылке с введённым значением,
ложится в `Set` при проверке повторов и сериализуется в `localStorage` без конвертаций.

### 1.2 Канонический вид попытки

`src/game/state.ts` — `normalizeGuess` вызывается ровно один раз, в `createAttempt`.
История хранит попытку в нижнем регистре (`'a0'`), а `hasTried` сравнивает с уже
каноническим значением. Следствия:

- проверка «эта попытка уже была» не содержит своего `toLowerCase`, то есть правило
  нормализации не дублируется;
- ввод `A0` и `a0` даёт один и тот же ключ истории → пункт чек-листа «повтор не приводит
  к задвоению»;
- интерфейс отображает историю капсом (`toUpperCase()` в `gameScreen.ts`) — это чисто
  косметическое преобразование, не участвующее в сравнениях.

### 1.3 Состояние игры — дискриминированное объединение

`src/game/types.ts`:

```ts
type GameState = ConfiguringState | RunningState | WonState;
```

| Вариант            | Обязательные поля                     | Какую невозможную конструкцию запрещает тип |
| ------------------ | ------------------------------------- | ------------------------------------------- |
| `ConfiguringState` | `draft`                               | «идёт игра, но секрета нет»                 |
| `RunningState`     | `config, secret, startedAt, attempts` | «раунд завершён, но времени финиша нет»     |
| `WonState`         | + `finishedAt`                        | «секрет известен, а настроек нет»           |

Почему не интерфейс с `secret: string | null` и `finishedAt?: number`: такое
представление требует проверок `if (state.secret !== null)` или оператора `!` в **каждом**
месте, где секрет используется, а `@typescript-eslint/no-non-null-assertion` (уровень
`recommended`, error) не пропустил бы последний вариант. Дискриминант `status` даёт
сужение типа бесплатно: после `if (state.status === 'running')` доступ к `state.secret`
типизирован без единого каста. Экран выбирается тем же дискриминантом (`app.ts` →
`render()`), поэтому «настройки нельзя менять после старта» не требует отдельного
механизма блокировки — экрана настроек в `running`/`won` просто нет.

### 1.4 История попыток — неизменяемый массив со структурным разделением

`src/game/state.ts`:

```ts
const attempts: readonly Attempt[] = [...state.attempts, createAttempt(...)];
```

| Решение                                             | Обоснование                                                                                                                                                                                                                                    |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `readonly Attempt[]`, а не `Attempt[]`              | мутация истории запрещена **компилятором**, а не договорённостью; в `tests/state.test.ts` есть тест с `@ts-expect-error` на `history.push(...)` — если `readonly` снять, `@ts-expect-error` станет неиспользуемым и `npm run typecheck` упадёт |
| пополнение через spread                             | каждая попытка — новый массив; прежние ссылки состояния остаются валидными (см. тест «leaves the previous state and its history exactly as they were»)                                                                                         |
| **без** глубокого клонирования записей              | элементы истории не изменяются никогда, поэтому переиспользование ссылок корректно и дешевле; это проверяется напрямую: `expect(newAttempts[0]).toBe(oldAttempts[0])`                                                                          |
| разделяемая `EMPTY_ATTEMPTS`                        | пустая история — константа; выделение нового массива на каждый рендер настроек не нужно                                                                                                                                                        |
| `finishRound` переносит **ту же** ссылку на историю | `{ ...state, status: 'won', finishedAt }`; тест `expect(won.attempts).toBe(afterMiss.attempts)` фиксирует, что завершение раунда не пересобирает историю                                                                                       |

Именно shallow-spread + замена вложенного массива — и есть иммутабельное обновление из
требования задачи: `{...state, attempts}` копирует верхний уровень, а новый вложенный
массив строится через `[...history, entry]`.

### 1.5 Результат попытки — сумма (sum type) вместо исключения или флага

`src/game/state.ts`:

```ts
type SubmitResultFor<S extends GameState> =
  | { status: 'accepted'; state: RunningState | WonState }
  | { status: 'rejected'; reason: SubmitRejection; state: S };
```

Три причины:

1. Ожидаемые отказы (`not-running`, `invalid-guess`, `already-tried`) — это **часть
   контракта**, а не аварийная ситуация: они происходят при нормальном пользовательском
   вводе. Исключение заставило бы UI оборачивать каждый клик в `try/catch`.
2. `reason` — данные, из которых UI строит сообщение (`describeRejection` в
   `messages.ts`). Текст не появляется в слое сравнения.
3. `state: S` при отказе гарантирует, что возвращается **тот же самый объект** (и рантайм:
   `rejected(state, reason)` возвращает вход без изменений). Проверка `Object.is` в
   `app.ts` (`setState`) из этого следует автоматически: отказ не порождает перерисовку,
   а история остаётся ровно той, что была.

Поле `state` успешной ветки сужено до `RunningState | WonState`, потому что принятой
попытка бывает только в активном раунде, а её результат — «раунд продолжается» или
«раунд выигран». Вариант `GameState` здесь был бы правдой «в принципе», но лишил бы тесты
и UI доступа к `attempts`/`secret` без проверок — что и проявилось как 15 ошибок
`TS2339` в CI до сужения.

### 1.6 Кэш мемоизации — `Map<string, CacheEntry<R>>`

`src/game/memoize.ts`.

- `Map` вместо `Record`/объекта: O(1) поиск по строковому ключу без прототипных коллизий
  (`'toString'`, `'constructor'` не являются ключами по построению, в отличие от проверки
  через `in`) и с предсказуемым порядком владения при отладке.
- Ключ — строка, собранная `keyOf` из **всех** аргументов. Дефолт `defaultKeyOf` склеивает
  все аргументы через `|`; для `countPossibleSecrets` передан свой `keyOf`, нормализующий
  `'dec'` и `10` в одно значение, чтобы в кэше не было двух записей на одну пару.
- Значение завёрнуто в `CacheEntry<R>` (`{ value: R }`). Без бокса `cache.get(key)` даёт
  `R | undefined`, и различить «в кэше нет» и «в кэше лежит `undefined`» можно было бы
  только через `has(...)` или оператор `!` (запрещён правилом `no-non-null-assertion`).
  Бокс даёт корректную семантику без единого каста.
- Кэш живёт в замыкании одного вызова `memoize`, а не в глобальной переменной: две
  обёртки над одной функцией не делят кэш (проверено тестом `gives each memoize call its
own cache`), а метод `cacheSize()` — интроспекция для тестов и отладки, не часть игры.

### 1.7 Таблица рекордов — отсортированный массив фиксированного размера

`src/game/records.ts`: `readonly ScoreRecord[]`, инвариант — **массив всегда
отсортирован по `compareRecords`**. Инвариант поддерживается на записи
(`insertRecord` = `[...records, rec].sort(cmp)`), поэтому чтение (`takeTop`) — это просто
`slice(0, n)` без сортировки. При `MAX_RECORDS = 10` это осознанный размен: дорогая
запись O(R log R) с R ≤ 10 дешевле, чем каждый рендер помнить, отсортирован ли вход.

Третий ключ сортировки (`finishedAt`) — не «запасной»: `Array.prototype.sort` стабилен, и
при `compareRecords === 0` порядок равен порядку в массиве, а он приходит из
`localStorage`. Без `finishedAt` два одинаковых по попыткам и времени результата могли бы
меняться местами между перезагрузками, то есть «топ-N» переставал бы быть детерминированным
наблюдаемым поведением.

### 1.8 Граница доверия: `localStorage` как `unknown`

`src/storage/localStorageRecords.ts` — эффект-адаптер: `getItem` → `JSON.parse` →
`sanitizeRecords` → `readonly ScoreRecord[]`. Он не знает ни правил сортировки, ни правил
валидации: они живут в чистом `records.ts` (`sanitizeRecords`, `isScoreRecord`) и
тестируются без браузера. Адаптер отвечает только за: ключ с версией
(`'bulls-and-cows:records:v1'`), отсутствие значения, некорректный JSON и недоступность
хранилища (приватный режим/квота) — через `try/catch` с возвратом `[]`/тихим отказом от
записи, чтобы игра оставалась играбельной без сохранений.

`isScoreRecord` отбирает только собственные числа корректного диапазона и имя базы,
проверенное через `Object.hasOwn(DIGITS_BY_BASE, value)`. Использование `in` вместо
`Object.hasOwn` пропустило бы запись с `base: 'toString'`, потому что
`'toString' in DIGITS_BY_BASE === true`; `Number.isFinite` отсекает `NaN` и `Infinity`,
которые иначе отравили бы компаратор (`NaN || NaN || NaN` → результат `NaN` → порядок
строк не определён).

### 1.9 Хранилище подписчиков состояния

`src/ui/app.ts` — `Set<Listener>` в замыкании `createStore`, обход через
`[...listeners]`: если обработчик отпишется или подпишется прямо во время рендера, порядок
доставки не зависит от внутренней реализации обхода `Set`. `setState` сравнивает
`Object.is(next, state)` — поэтому возврат состояния «как есть» из отказной ветки
`submitAttempt` не вызывает перерисовку.

## 2. Алгоритмы

### 2.1 `generateSecret(length, base, random = Math.random)`

`src/game/pickFrom` + `buildSecret`, без `splice` и `while`:

```
pool ← алфавит базы (уникальные символы по построению)
build(pool, 0) = ''
build(pool, n) = let i = floor(random() * |pool|)
                 in pool[i] + build(pool без индекса i, n - 1)
```

- «Без повторений» обеспечивается структурой данных, а не проверкой: алфавит базы не
  содержит дублей, а выбранный символ исключается из пула иммутабельно
  (`pool.filter((_, position) => position !== index)`).
- Распределение равномерное по всем `P(base, length)`: на первом шаге каждый из `base`
  символов выбирается с вероятностью `1/base`, далее — по тому же аргументу от уменьшенного
  пула, то есть вероятность любой последовательности `1/(base·(base−1)·…·(base−length+1))`.
- Источник случайности — параметр. Это делает функцию проверяемой на **точных**
  ожиданиях: `() => 0` даёт первые `length` символов алфавита, `() => 0.999999` — последние,
  скриптованный источник `[0, 0.5, 0.9]` для dec/3 даёт `059`. Число обращений к источнику
  ровно `length` — проверено счётчиком (`createCountingRandom`).
- Гварды: `length > |pool|` → `RangeError` (секрет невозможно построить), сломанный
  источник (`random() === 1`) → `digitAt` бросает `RangeError`, а не возвращает
  `undefined` (следствие `noUncheckedIndexedAccess`: обращение по индексу — это
  `string | undefined`, и `!`/`as` запрещены стилю).

### 2.2 `evaluateGuess(secret, guess) → { bulls, cows }`

Формальное определение, реализованное в коде:

```
B = { i : s_i = g_i }                                  (быки)
cows = |мультимножество(g \ B) ∩ мультимножество(s \ B)|
```

Реализация (`src/game/evaluateGuess.ts`):

1. `toDigits` приводит **обе** строки к нижнему регистру один раз. Дальнейшие сравнения о
   регистре не думают. Если бы нормализовалась только одна сторона, для секрета
   `secret = 'a1'` и ввода `guess = 'A1'` получилось бы `bulls = 0`, `cows = 2`, и при
   hex-вводе в верхнем регистре `bulls` физически не мог бы достичь `length` — то есть
   партия не заканчивалась бы вообще. Тест `evaluateGuess('AB12', 'ab12') = 4/0`
   документирует симметричность контракта.
2. `partition` строит три массива тремя `filter` (никаких счётчиков): быки, «цифры
   попытки не на своих позициях», «цифры секрета, не совпавшие с попыткой по своей
   позиции». Массив быков используется как единственное число (`bulls.length`) — повторного
   пересчёта нет.
3. `countMatched` считает пересечение через `reduce` с иммутабельным аккумулятором
   `{ count, remaining }`: найденное вхождение удаляется из `remaining` через
   `slice`/spread, а не `splice`. Отсюда **множественная** семантика: каждая цифра секрета
   закрывается не более одного раза.

Почему именно множественная семантика, если в игре она не отличима: при уникальных цифрах
обе формулировки («встречается в секрете, но не на своей позиции» и «пересечение
не-быковых позиций») дают одинаковый результат — это можно вывести из уникальности: если
`s[i] = g[i]`, то никакая другая позиция попытки не равна `s[i]`. Различие проявляется
только на невалидном входе, который игра не производит. Тем не менее закреплена именно
множественная версия, потому что `evaluateGuess` не должен зависеть от пред-условия
вызывающего: тест `evaluateGuess('1234', '2114') = 1/2` (наивный `includes` даёт `cows = 3`)
делает функцию тотальной и независимо тестируемой.

Следствие для равенства `digitAt(...) === digitAt(...)` при `?? ''`: пустая строка не
совпадёт ни с одной настоящей цифрой, а `'' === ''` невозможно, потому что каждый `filter`
итерируется только по своей строке и его индексы всегда внутри её длины — то есть
внедиапазонные пары не сравниваются. Именно поэтому сравнение с заглушкой `''` безопасно.

### 2.3 `isValidGuess(guess, length, base)`

Конъюнкция трёх неэкспортируемых предикатов, выстроенных по возрастанию стоимости:

```ts
hasValidLength(guess, length) &&
  hasOnlyValidDigits(guess, base) &&
  hasNoRepeats(guess);
```

| Предикат             | Что делает                                           | Стоимость                                            |
| -------------------- | ---------------------------------------------------- | ---------------------------------------------------- |
| `hasValidLength`     | `guess.length === length`                            | O(1)                                                 |
| `hasOnlyValidDigits` | `guess.split('').every(createDigitValidator(base))`  | O(n), `every` выходит на первом недопустимом символе |
| `hasNoRepeats`       | `new Set(guess.toLowerCase()).size === guess.length` | O(n)                                                 |

Ключевое решение — порядок: длина стоит первой, поскольку она O(1) и отсекает большую
часть неверных вводов до построения набора символов; валидация символов стоит раньше
проверки повторов, потому что `every` коротко замыкается. Повторы в hex ловятся
нормализацией регистра **до** построения `Set`, поэтому `Aa`, `aA`, `aa` — это один и тот
же повтор. Порядок сравнения цифр «регистрация → множество» — тот же, что в `evaluateGuess`
и `hasTried`: одно правило нормализации на всё приложение.

### 2.4 `countPossibleSecrets(length, base)`

Рекурсия ровно по связи из задания, с мемоизацией:

```
f(0, k)      = 1                                  (пустая последовательность — одна)
f(n, k)      = 0                     , если n > k (цифр не хватает — 0 секретов)
f(n, k)      = k · f(n-1, k-1)       , иначе       (выбор первой цифры × остаток)
```

- Ноль в начале **не вычитается**: секрет — строка, поэтому `P(base, length)` берётся
  как есть. Проверочные значения из тестов: `f(2,2) = 2` (`01`, `10`), `f(2,10) = 90`
  (не 81), `f(3,10) = 720` (не 648), `f(6,16) = 5765760`.
- Равенство `n = k` разрешено и даёт `k!` (`f(8,8) = 40320`) — секрет, использующий весь
  алфавит. Сравнение `>` , а не `>=`: последнее отрезало бы этот случай.
- `n > k` возвращает `0`, а не бросает: у комбинаторной величины есть корректный ответ, и
  именно его UI показывает как «0 секретов» / блокировку длины. Ошибкой являются только
  величины вне комбинаторного домена — отрицательная или нецелая длина (`RangeError`),
  иначе рекурсия с `2.5` никогда не дошла бы до базы `n === 0`.
- Мемоизация на уровне модуля: `memoize` оборачивает функцию **один раз**, и рекурсивный
  вызов обращается уже к мемоизированной привязке. Вариант
  `(n, k) => memoize(step)(n, k)` формально «тоже мемоизирован», но кэш живёт одну строку и
  никогда не используется — подзадача `(3, 9)` из цепочки `f(4, 10)` обязана попадать в тот
  же кэш, что и прямой запрос `f(3, 9)`.
- Кэш ограничен по размеру: ключи — это пары «длина × размер алфавита», длины `0..6`,
  размеры `0..16` (внутренние вызовы используют и размеры `9`, `8`, `7`…, которых нет среди
  реальных баз), то есть максимум `7 · 17 = 119` записей. Тест
  `keeps the cache bounded` сверяет именно эту границу; абсолютные значения (`toBe(84)`) в
  тестах кэша не используются, потому что кэш модульный и его размер зависит от порядка
  запуска файлов.
- Арифметика точна: максимум по домену — `16! = 20 922 789 888 000 ≈ 2.09·10¹³`, что меньше
  `Number.MAX_SAFE_INTEGER ≈ 9.01·10¹⁵`, поэтому `number` даёт точное значение и `BigInt`
  не нужен. Это граница домена, а не совпадение: при длине 17 в hex уже потребовался бы
  другой тип.

### 2.5 `submitAttempt` — конвейер гвардов

`src/game/state.ts`, последовательно и без вложенных условий:

```
не running        → rejected 'not-running'   (тот же объект состояния)
не валидно        → rejected 'invalid-guess' (тот же объект)
уже было          → rejected 'already-tried' (тот же объект)
иначе             → attempt = createAttempt(guess, evaluateGuess(secret, guess), now)
                    attempts' = [...attempts, attempt]
                    isWin? → accepted finishRound({...state, attempts'})
                          → accepted {...state, attempts'}
```

Победа определяется **только** быками: `isWin(score, length) ⇔ bulls === length`. Попытка
`3210` против секрета `0123` даёт `cows = 4 = length`, но не является победой — этот
случай закреплён отдельным тестом (`isWin({bulls: 0, cows: 4}, 4) === false`), потому что
наивное `bulls + cows === length` завершает партию с незавершённой игрой.

### 2.6 `records.ts` — сравнение и обновление таблицы

```ts
compareRecords = (a, b) =>
  byAttempts(a, b) || byElapsed(a, b) || byFinishedAt(a, b);
```

Использование `||` корректно, потому что «нет разницы» — это `0`, ложное значение; каждый
критерий — отдельная именованная функция по одному полю, и правило читается как
предложение: «по попыткам, затем по времени, затем по моменту завершения». Антисимметрия
проверена свойством на全部 парах фикстур, рефлексивность — на копиях записей.

`insertRecord` вызывает `sort` на **свежесозданном** массиве (`[...records, record]`):
`sort` мутирует получатель, но мутится не вход, а локальная копия. Аналогично в
`sanitizeRecords` (`filter` уже даёт новый массив). `registerRecord = takeTop(MAX_RECORDS)
∘ insertRecord` — композиция двух чистых функций, где `takeTop` каррирован и потому
применим и для превью (`takeTop(5)`), и для записи.

### 2.7 Правила настроек (`settings.ts`) — ограничение длины вычисляется

`isLengthAllowed(length, base) ⇔ MIN ≤ length ≤ MAX && countPossibleSecrets(length, base) > 0`.

В двоичной системе активна только длина 2 не потому, что в UI есть ветка
`if (base === 'bin')`, а потому что у длин 3–6 в двоичной системе **ноль секретов**.
Ограничение и подсчёт пространства — один источник истины, поэтому они не могут разойтись
при правке алфавита.

Два разных отказа у двух действий — сознательные: смена базы легитимна и **корректирует**
черновик (`selectBase` понижает длину до максимальной допустимой,
`min(MAX, |алфавит|)`), смена длины на невозможную **игнорируется** (`selectLength`
возвращает тот же объект), потому что такой клик — аномалия ввода, а не операция.

### 2.8 Интерфейс: `render = f(state)` и одно исключение

`render()` в `app.ts` строит экран целиком (`replaceChildren` + фабрика `el`) — при
размерах дерева в десятки узлов полная перерисовка дешевле диффа и не содержит багов
синхронизации. Единственное исключение — тикающие часы: `updateClock` меняет `textContent`
одного `<span>`, иначе каждые 500 мс пересоздавался бы `<input>` и терялся набранный ввод.
Перед каждой полной перерисовкой `clockUpdater` обнуляется, чтобы интервал не писал в узел,
уже удалённый из DOM, а `stopClock`/`unsubscribe` входят в teardown.

Весь ввод проходит через чистые функции ядра: фильтр символов — `createDigitValidator`
(второе применение карринга после `isValidGuess`), допустимость попытки — `isValidGuess`,
повтор — `hasTried`, сравнение — `evaluateGuess` внутри `submitAttempt`. В UI нет ни одной
строки игровой арифметики, поэтому все правила уже покрыты юнит-тестами без браузера.

## 3. Вычислительная сложность

Обозначения: `n` — длина секрета и попытки, `b` — размер алфавита базы, `a` — число
попыток в истории, `R` — число записей рекордов, `k` — кэш-ключ.
Игровой домен: `2 ≤ n ≤ 6`, `b ∈ {2, 8, 10, 16}`, `a` не ограничено (лимита попыток нет),
`R ≤ MAX_RECORDS = 10`.

### 3.1 Обязательные четыре функции

| Функция                | Время                                                           | Память                                                           | Обоснование                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `generateSecret`       | **O(n·b + n²)**, при игровых границах — константа               | **O(n·b)** пиково                                                | `buildSecret` делает `n` шагов рекурсии; на каждом `pool.filter` проходит по пулу размером ≤ `b` → `O(n·b)`. Склейка `value + rest_string` копирует накопленную строку → арифметическая прогрессия `1+2+…+n` → `O(n²)`. Память: исходный пул `O(b)` плюс по одному живому пулу на каждом уровне стека (`n` копий, каждая ≤ `b`) + результат `O(n)`. Обращений к источнику случайности — ровно `n` (это инвариант, проверяемый тестом со счётчиком): лишнего «броса» на проверку повторов нет, уникальность обеспечивается самой структурой пула                                                                                                                |
| `evaluateGuess`        | **O(n²)**                                                       | **O(n)** живая / O(n²) выделяемой                                | `toDigits` — 2×O(n). `partition` — три `filter` по O(n) каждый, итого O(n) и три массива длиной ≤ n. `countMatched` — по `k ≤ n` кандидатам: `indexOf` по `remaining` (≤ n) плюс восстановление массива через два `slice`+spread (≤ n) → **O(k·n) = O(n²)**. При n = 6 это 36 операций — шум; квадрат появляется из иммутабельного удаления элемента, и это сознательный размен: линейный вариант потребовал бы изменяемого `Map` счётчиков, то есть мутации аккумулятора внутри reduce                                                                                                                                                                        |
| `isValidGuess`         | **O(n)** (формально O(n·b), где `b ≤ 16` — константа)           | **O(n)**                                                         | `hasValidLength` — O(1). `hasOnlyValidDigits`: `split` O(n), далее `every` с `includes` по алфавиту фиксированного размера (≤ 16) → O(n); `every` коротко замыкается, поэтому на «мусорном» вводе время ближе к O(1). `hasNoRepeats`: `toLowerCase` O(n) + построение `Set` из n элементов → O(n) и O(n) памяти. Порядок конъюнкции (`&&`) гарантирует, что второй и третий предикаты вообще не выполняются при неверной длине                                                                                                                                                                                                                                 |
| `countPossibleSecrets` | **O(n)** без кэша, **O(1)** амортизированно при попадании в кэш | **O(n)** стек + **O(1)** кэш при игровых границах (≤ 119 ключей) | Без кэша рекурсия делает `n` шагов до базы `n = 0` (или до гварда `n > b`), на каждом — одно умножение и один вызов, стек глубиной `n`. Умножение — O(1), потому что максимум по домену (`16! ≈ 2.09·10¹³`) лежит внутри точной целой арифметики `number` (`< 2⁵³−1`), то есть не нужно ни `BigInt`, ни длинная арифметика. С мемоизацией повторный запрос пары — это построение ключа O(1) + один `Map.get`; первый запрос добавляет `n+1` ключей, но подзадачи переиспользуются между запросами (`f(4,10)` и прямой `f(3,9)` — одна и та же запись), поэтому размер кэша растёт не с числом вызовов, а с числом **различных** пар и ограничен `7 · 17 = 119` |

### 3.2 Остальные функции ядра (для полноты)

| Функция                                                                     | Время                                      | Обоснование                                                                                                                                                                                                                                                |
| --------------------------------------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `memoize` (обёртка)                                                         | O(1) амортизированно на вызов              | построение ключа из 1–2 аргументов + `Map.get`/`Map.set`; при исключении кэш **не** пишется (тест `does not cache a thrown failure`), чтобы временный сбой не «замерз» в кэше                                                                              |

| `sanitizeRecords`                                                           | O(R log R) + O(R) на `JSON.parse`          | `filter` с type-guard, затем `sort`, затем `slice`                                                                                                                                                                                                         |
| `readRecords` / `writeRecords`                                              | O(R) / O(R)                                | один `getItem`/`setItem`; размер не растёт из-за `MAX_RECORDS`                                                                                                                                                                                             |

| `countPossibleSecrets` в UI                                                 | вызывается при каждой перерисовке настроек | для этого и нужен кэш: экран настроек перерисовывается на каждое переключение длины/базы, и пересчитывать `P(b, n)` заново незачем                                                                                                                         |

## 5. Инварианты, которые поддерживаются везде

1. `secret.length === config.length` и `2 ≤ config.length ≤ alphabetSize(base)`;
   `alphabetSize = 2/8/10/16` для bin/oct/dec/hex.
2. Все цифры секрета и всех принятых попыток уникальны (обеспечено алгоритмом генерации и
   `hasNoRepeats`, а не проверкой после факта).
3. Любое сравнение цифр — после приведения к нижнему регистру; канонический вид хранится в
   истории.
4. История раунда неизменяема: элементы не изменяются и не удаляются, новые только через
   новый массив; отказ в попытке не изменяет ничего.
5. `bulls === config.length` — единственный признак победы.
6. Таблица рекордов всегда отсортирована по `compareRecords` и содержит не более
   `MAX_RECORDS` записей; у каждой записи указаны `length` и `base`, поэтому общий список
   однозначен (бейдж `hex · 4 цифры` в `scoreboard.ts`).
7. Ядро не имеет побочных эффектов и не читает глобальных источников времени/случайности/
   хранилища.
8. Каждое состояние `GameState` содержит ровно те поля, которые требует его вариант —
   невозможные комбинации исключены типом.

## 6. Что сознательно оставлено проще, и почему

| Решение                                                           | Альтернатива                                   | Почему выбрано это                                                                                                                                            |
| ----------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `evaluateGuess` с `indexOf` + `slice`                             | `Map` счётчиков, O(n)                          | линейный вариант требует изменяемого аккумулятора; при n ≤ 6 выигрыш — 30 операций, потеря — чистота `reduce`                                                 |
| Полная перерисовка экрана                                         | дифф/виртуальный DOM                           | дерево ≤ нескольких десятков узлов; дифф добавил бы кода больше, чем багов, которые он предотвращает. Исключение — часы (см. 2.8)                             |
| Одна общая таблица рекордов с бейджем настроек                    | отдельная таблица на каждую пару `length/base` | оба варианта разрешены заданием; общий список короче, а бейдж делает контекст записи явным                                                                    |
| Сохраняются только рекорды, не состояние раунда                   | сериализация `GameState`                       | «переживает перезагрузку» требуется именно для рекордов; сериализация состояния потребовала бы версионирования и миграций ради функции, которой в задании нет |
| Лимита попыток нет                                                | максимум N попыток                             | так в задании; поэтому `submitAttempt` — O(a), а не O(1), и это учтено в сложности                                                                            |
| `takeTop(0)/takeTop(-1) → []`                                     | `slice(0, count)`                              | `slice(0, -1)` означает «всё, кроме последнего», то есть тихая подмена смысла при ошибке в аргументе                                                          |
| `Object.hasOwn` вместо `in`                                       | `in`                                           | `in` считает собственными свойства прототипа: `'toString' in DIGITS_BY_BASE === true`, и запись с `base: 'toString'` прошла бы валидацию                      |
| `toBe` (`Object.is`) в тестах ядра                                | `toEqual`/`===`                                | строже: различает `+0/−0` и `NaN`; нашло две реальные ошибки в тестах (знак нуля в оракуле `P(n,k)` и в property-тесте `Math.sign`)                           |
| `pre-commit` только `lint-staged`, `pre-push` — typecheck + тесты | тесты в pre-commit                             | иначе красные тесты (обязательный первый шаг TDD) сделают коммит невозможным; при этом запушить красный коммит поодиночке всё равно нельзя                    |

## 7. Заметки о самих тестах (первоисточник нескольких решений выше)

- **Инъекция вместо случайности.** `generateSecret` принимает `random`, поэтому тесты
  ожидают **точные** строки (`012`, `987`, `059`), а не «похоже на случайное»;
  воспроизводимость даёт фиксированный seed, независимость — свой источник в каждом тесте.
  Тесты сравниваются с закрытой формулой `P(n,k)`, а не с копией рекурсии.
- **Оракул обязан знать свою область определения.** `permutations` в тестах
  `countPossibleSecrets` возвращает `0` при `length > digitCount`: без этого произведение
  `2·1·0·(−1)` даёт `-0`, и `Object.is` в `toBe` честно сообщение «expected +0 to be -0».
- **Красный тест может быть неправ — и был неправ трижды.** (1) Ожидался `RangeError` для
  `length 5` в oct, хотя `5 ≤ 8` и `P(8,5) = 6720` законны. (2) Тест просил `RunningState`
  на победной попытке, которую `submitAttempt` всегда завершает сам, — такой промежуточной
  фазы в контракте нет. (3) В ожиданиях порядка рекордов `[r2, r3]` противоречил
  собственному правилу «при равных попытках быстрее тот, у кого меньше времени»
  (`60 000 < 120 000`). Критерий в каждом случае: реализация согласована с доменом и
  правилом, а expectation им противоречит → правится тест, а код не трогается; «починить»
  компаратор `Math.abs`-обёрткой значило бы добавить защиту от несуществующего бага.
- **Тесты не должны зависеть от порядка запуска.** Кэш мемоизации модульный, поэтому в
  `countPossibleSecrets.test.ts` сравниваются только дельты (`afterFirst`,
  `cacheSize() ≤ 119`), а не абсолютные значения; иначе любой другой файл, обратившийся к
  функции раньше, сломал бы утверждение.
- **Независимость модулей в тестах.** Тесты `evaluateGuess` и `generateSecret` не вызывают
  друг друга и не используют `isValidGuess`: иначе падение одного модуля сделало бы
  красными тесты другого, и «падает всё сразу» перестало бы быть диагностичным.
- **Проверка на уровне компиляции.** `@ts-expect-error` перед `history.push(...)` в
  `state.test.ts` — это assertion: если `readonly` снять, директива станет неиспользуемой,
  и `npm run typecheck` упадёт. Именно поэтому контракт иммутабельности нельзя «случайно»
  ослабить, отредактировав только типы.
